# November 18: hold actions, debug hint and load refusal

Baseline: public v0.4.6, application tag 7cce754; branch starts at documentation
main 787ba95. The owner reports failed weight-hold Auto Load, debug guidance
interrupting ordinary roughly two-second holds, and a further tap-to-load failure.

## What the new report establishes

CONFIRMED (inbox report bb697e8f, firmware 0.4.6): two weight actions were classified
hold=1 and reached Explicit Auto Load action at 111270/115402 ms. The first status
is "Safety status 0 unrecognized". A later weight tap, hold=0 at 264480 ms, records
the same refusal and opens the control notice. Preset hold=1 also reached its
override page. Thus the submitted Auto Load attempts were recognized; the hint
alone is not their cause.

The refusal snapshot records accepted/activated=1, direct motor=0 aged 270 ms,
mode=1, base 40 LB, unit0, max230, position=offset=13, child lock0, OTA0, mount 2,
EP_VOID_LOCK 21224=0 aged 1359 ms, Auto Load status0, standalone coworker zero/zero.
The current context again shows a fresh zero. Earlier report 373b873f on 0.4.4
also refused fresh zero. No load/Auto Load request result is logged for the new
attempts because refusal occurs before sending the request.

CONFIRMED (source): the application accepted EP_VOID_LOCK only at 6 from Black's
October 24 successful profile. Android da514d2's
[parameter catalog](https://github.com/dylanmaniatakes/Beyond-Power-Voltra-Android/blob/da514d2db1a16ebb4ded3156bc8fd200bed1e6eb/app/src/main/assets/voltra/paramInfo.csv)
defines 21224 as volatile uint32, default 0; mask 21227 defaults to all bits, and
history 21371 is separate. Refreshed SDK 79f6c55, Android da514d2, HA 93b0819 and
Kirby 8e1ea1c provide no general interpretation of this field's bits.

The bounded explicit-load compatibility rule now accepts only fresh exact 0 or 6.
INFERRED: the catalog default and reported zero are compatible with the existing
otherwise-ready load profile. This is not a manufacturer-confirmed safe/no-fault
enum or permission to accept arbitrary lock values. Missing/stale/other values
remain blocked. Independent mount, activation, mode, child lock, OTA, direct motor,
standalone/peer freshness, base/limits and Auto Load conditions stay unchanged.
Tap Load still needs known cable zero; Auto Load keeps its existing known-cable
policy and does not acquire a new retracted-cable restriction.

Scope is explicit Load/Auto Load readiness only. Live base/modifier/dropset writes
retain the previous status 6 requirement and active motor 5 remains unsupported.
This release does not claim to repair RP. No field/mask is cleared or written,
no force path or retry is introduced, and the existing one-shot AA12 trigger is
unchanged. Auto Load refusals now retain the same bounded snapshot/notice as tap
refusals and log request results; snapshots include enabled/safety fields too.

## Hold recognition and hint

CONFIRMED (LVGL 9.3 source): CLICKED occurs on release after long presses, but
LONG_PRESSED is detected while processing pressed samples. A frame/GATT stall
can cross 650 ms and reach a release without the separate long-press callback.
The application previously relied on that callback's held flag. That is a
reliability gap, not a proven cause of the report's already-recognized holds.

The K5 touch adapter now exposes its existing capture timestamp. Ordinary actions
classify capture-time duration on release, avoiding both a missed long-press
callback and a processing delay inflating a short tap. Synchronous adapters fall
back to their processing clock. Existing stale/cancel, movement, wake-only and
screen-change rules remain. The ordinary threshold stays 650 ms; a roughly two-second
hold then release therefore invokes Auto Load/preset override rather than a tap.

No hint is displayed until 3000 ms. Then it reads "Keep holding to send a debug
log". At 6000 ms, the debug gesture consumes the action and opens the report dialog.
The release handler also protects the threshold boundary; it cannot first load
and then enter debugging. No Auto Load is fired while the finger is still down.
