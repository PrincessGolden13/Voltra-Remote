# November 14: debug access, dropset state and load refusal

Baseline: published v0.4.3, commit d09b0b4731d3c29fe54d8b04f47604d8c3387bee.
The owner reports that a six-second hold did nothing, RP changed the remote's
number without changing the VOLTRA, and loading White from the remote was
refused even though settings and externally started training worked.

## Debug access

Settings now has **Send debug log**, using the same consent dialog and bounded
20-event inbox as the hold. A load refusal opens a persistent, readable notice
with Send debug log, Back and Unload. Nothing is transmitted before YES.
The most recent control failure's numeric state is retained in a bounded,
RAM-only context snapshot so leaving the connection for Settings does not erase
the evidence. Manual disconnect also retains the last numeric session snapshot.
These snapshots may describe an earlier connection in the same boot;
its timestamp is included. OTA/NVS layout and preferences are unchanged.

CONFIRMED (manufacturer register documentation): CST816S 0xFB can reset after
five seconds without a recognized gesture; 0xFC resets on a long press. Zero
disables these touch resets. The K5 driver previously configured only 0xFE
(disable sleep), leaving the reset timers at their defaults. It now writes
0xFB=0, 0xFC=0, 0xFE=1 and logs ACK/readback. INFERRED: a controller reset can
explain the failed hold; this has not been captured on the owner's board.

- [CST816S register description, 2019-08-30, pages 5-6](https://cdn.static.spotpear.com/uploads/picture/learn/common-lcd/lcd/1.28inch-round-lcd/CST816S%20Register%20Description-20190912.pdf)
- [Waveshare-hosted register declaration](https://files.waveshare.com/upload/c/c2/CST816S_register_declaration.pdf)

The screen-wide debug hold now permits 10% display-side drift independently of
the stricter tap/swipe threshold. A noninteractive countdown appears after one
second. Invalid/stale touch samples and larger movement still cancel; a waking
touch is still wake-only. Release after six seconds cannot perform the underlying
tap or Auto Load action. Ordinary control holds retain their release behavior.

## Readiness and loaded weight writes

CONFIRMED (source): kirby6365/voltra_remote remains at
8e1ea1cb752acd3108c61f1a502b63978a172832 (GitHub rechecked November 14).
[Its protocol notes](https://github.com/kirby6365/voltra_remote/blob/8e1ea1cb752acd3108c61f1a502b63978a172832/docs/PROTOCOL.md)
document a bulk settings push reporting motor 1 while a direct read reports 5,
and an active-set weight write dropping mode 5 to 1. That implementation
reissues motor command 5 to apply the setting to the active set. Our standing
explicit-load rule excludes this automatic reload/retry technique.

The existing idle-only base-write path could therefore be authorized by a stale
bulk echo. It now also requires a fresh direct motor read. The specific bulk
mode-1 echo cannot replace a fresh direct mode-5 observation; single-field changes,
unload/unknown values and genuine direct readbacks remain effective. Active mode
5 remains unsupported for live edits, with a specific explanation. No motor
command was added to dropsets. The exact effect failure on the user's machine
remains UNVERIFIED; this release must not be described as fixing active-set RP.

Required safety/link polls no longer bundle the optional paired-ID, rest-time
and Auto Unload holding-time parameters into the same request. Unsupported
optional fields can otherwise reject a complete required response. A reported
paired field and the RP holding-time limit get separate critical polls; missing
or stale safety information still blocks loading. The 2-second freshness policy
and exact accepted safety values are unchanged. Explicit loading additionally
requires a fresh direct unloaded motor report.

Load refusal distinguishes missing link status, unsupported Twin/link state,
activation, update, lock, Auto Load, cable and motor conditions. The exact White
failure remains unknown without its report; no new safety-state value is assumed.
Parameter writes, changed base values, settled readbacks and drop failures now
enter the ring. Drop traces include requested ticks/unit and measured force;
register confirmation is explicitly not proof of physical resistance.
